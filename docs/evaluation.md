# 同库持续进化评测

主要问题是持续获得反馈后，对同一个业务数据库的未见问题能否改善。每个数据库使用相同初始 Skill 的独立分支，最终报告各库结果和跨库宏平均。

## 准备与运行

从 BIRD 官方获取数据并解压，将题目 JSON 和数据库目录放在本地。下面的示例假定题目位于 `data/bird/train.json`，数据库位于 `data/bird/databases/<db_id>/<db_id>.sqlite`，可通过参数指定实际位置。[BIRD 数据入口](https://bird-bench.github.io/)

示例每组使用 10 题，用于检查整个流程并估算调用成本。准备 `.env` 中的模型配置后，在项目根目录执行。

```sh
uv run --locked evogate-eval prepare \
  --workspace workspaces/bird-stream \
  --source data/bird/train.json --db-root data/bird/databases \
  --db-ids works_cycles --per-split 10 --batch-size 5 --rounds 2 \
  --env-file .env --max-calls 1000 --workers 4

uv run --locked evogate-eval run \
  --workspace workspaces/bird-stream --env-file .env --workers 4
```

`prepare` 本地预检参考 SQL、固定模型和数据清单、初始化通用 SQL Skill，并将所有 training 题标为尚未释放。可用 `--skill /absolute/path/SKILL.md` 指定初始 Skill。

`run` 每个窗口最多释放 `batch-size` 道题。目标 Agent 先用当时已发布版本回答，再记录参考反馈，之后从已释放经验进行一次修订与验证。达到窗口上限或经验流耗尽后固定最终版本，运行保留集对照。

窗口机制复用应用的经验存储、回放选择和发布逻辑。评测按预先固定的窗口尝试更新，产品中的自动调度使用新反馈数量与重复失败条件。

候选文档与当前版本相同时，跳过候选开发集与验证集评测，进入下一批经验。与历史未发布候选完全相同、且数据库文件状态、业务上下文、模型、当前版本、验证案例和门槛相同时，复用已完成的验证结论，也跳过候选评测；历史评分不完整时会重新验证。生成提案前仍需获取当前开发反馈，每个窗口都保留尝试记录。

## 数据边界

每个数据库按去除字面量后的 SQL 模板分组，分为 training、selection、holdout，并去重问题。这能减少可识别的近重复。正式结论还需检查语义相近的题目家族。

- training 题的反馈随窗口释放，可进入优化器。
- selection 是验证集，决定发布。题目、答案和逐题轨迹不传给优化器，也不进入经验回放；门禁原因、汇总分数与改善／退化数量会影响后续优化。反复筛选会对验证集产生适配，因此最终收益需看 holdout。
- holdout 是保留测试集，在全部更新结束后比较初始 Skill、最终 Skill 与无 Skill。标签保存在本地，优化器无法访问。若根据其结果继续调参，这批题就成为已观察的测试数据；正式报告应另留未参与调参的测试题。

`--rounds × --batch-size` 小于 training 题数时，后面的题不会释放，实际使用量保存在 `released_task_ids`。根据每库题量、重复模板和调用预算选择样本数。先固定数据库选择与划分，再查看模型表现。

记录数据此前是否用于开发或调参。这里的划分用于同库自定义评测。BIRD EX 使用集合相等，忽略行序与重复行，需要结合题意解释。

## 发布策略

候选、当前版本、初始 Skill 使用同样模型、工具与任务预算。选择集逐题配对的净改善达到 `min_net_improvements`，且候选达到初始 Skill 成绩时发布。默认门槛为 1 题，可在 prepare 时用 `--min-net-improvements` 配置，`--replay-size` 设置经验回放数量。策略随协议冻结，run 会校验一致性。

净退化拒绝，净收益不足或缺少可用评分时待定，经验持续保留。发布规则是工程选择标准，最终收益及稳定性由保留集和必要的重复运行检验。

优化器接收补丁最终校验结果、门禁原因，以及开发案例修改前后的 SQL 和评分。旧提案理由中的中间修复错误仅作为模型历史表述，最终门禁结果用于判断未发布原因。重复候选引用原评测版本的开发证据，优化器可修订适用条件或处理其他已有证据支持的问题。

当前门禁要求所有验证题评分已知。参考 SQL 执行成功时，模型 SQL 超出明确的结果行数、结果总大小或 SQLite 单值大小限制计为 0 分。数据库故障、无法归因的进程退出等仍记为未知；参考 SQL 失败也记为未知。缓存中的未知观测会重新执行原 SQL 并评分，已生成的历史报告保留原结果。

## 恢复与成本

工作区保存待完成窗口及其起始版本、已释放题目、候选文档和逐题观测。中断后重新执行同一条 `run` 命令，先完成当前窗口。候选缓存校验 Skill、经验、预算和开发上下文。命令行评测在终端进程中运行，长任务可使用 tmux 等工具管理。

`--max-calls` 覆盖整个评测运行，包含提案、修复、回放、门禁和最终比较。保持模型配置、程序版本及数据库内容一致。建议使用固定 SQLite 副本。

`--workers` 设置题目任务并发数，覆盖经验窗口、候选验证和最终三组对照。各题内的工具调用仍按顺序执行，进化轮次按经验顺序推进。本地 SQL 最多同时执行 4 条，以便增加模型请求并发时控制本机资源占用。

编辑预算独立于模型调用预算。新运行默认每轮最多 3 处编辑，增删字符总额度为 `min(4000, max(1200, 正文字符数 × 0.3))`。`--min-edit-chars` 设置短文档额度下限，`--max-edit-chars` 设置绝对上限，`--max-edit-ratio` 设置正文比例。替换同时计算删除和插入字符，额度包含插入的分隔换行。1200 是为短初始 Skill 选用的工程默认值，收益仍需评测。

优化器接收实际额度和绑定原文 SHA 的段落编号，通过 `target_id` 定位整段。插入在完整段落之后，替换提交整段新文本；旧的精确文本 `target` 补丁仍可重放。格式修复会收到失败编辑序号、已用额度和该编辑成本。旧评测协议缺少 `min_char_budget` 时保持原比例预算，`--min-edit-chars 0` 可显式使用该规则。比较新旧优化器应使用独立工作区，保留原实验记录。

## 输出

| 文件 | 内容 |
|---|---|
| `round-protocol.json` | 数据、模型、初始 Skill、窗口、轮数与总调用预算 |
| `preflight.json` | 参考 SQL 可执行性与排除项 |
| `state.json` | 分支、释放进度、经验与每次候选决策 |
| `candidates/` | 候选及上下文哈希 |
| `observations/` | 开发和门禁逐题观测 |
| `requests/requests.jsonl` | 模型调用、响应与用量 |
| `frozen-*.json`、`evaluations/` | 最终快照与可恢复的三组观测 |
| `report-*.json` | 初始、进化、无 Skill 的 EX、逐题结果与查询成本 |
| `summary.json` | 各库收益、改善与退化题数、发布历史、宏平均与总调用用量 |

发布结果时应同时提供数据来源与划分、代码版本、模型配置、初始 Skill、每库样本数、三组准确率、改善／退化题数及调用成本。测试集中较小的收益应通过配对复跑检查稳定性。

已观察过结果的测试集用于工程对照时，应注明其使用历史。
